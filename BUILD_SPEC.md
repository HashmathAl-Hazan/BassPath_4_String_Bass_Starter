# BassPath — implementation specification

## Goal and scope
Build a working responsive learning website for a complete beginner on **four-string fretted bass, standard E1–A1–D2–G2**. The learner practises about 30 minutes a day and wants dependable worship/band playing and learning by ear. Timing, relaxed control and muting precede speed. Teach through short explanations, demonstrations, deliberate practice and review. Use the supplied original JSON curriculum; do not generate placeholder lessons or scrape teaching sites.

This pack is input for a coding agent, not a prebuilt website. Implement all core features below in this task, in small slices. Advanced technique lessons are optional study, not a requirement for playing with a band. Milestones are self-assessments, not professional qualifications.

## Stack and boundaries
Use Next.js App Router, TypeScript, Tailwind CSS, local JSON and native Web Audio. Prefer existing compatible dependencies if a project already exists. Use current compatible stable versions, a lockfile, and the Node version required by the installed Next.js release. Do not blindly reuse an obsolete `next lint` command; configure an actual lint script. Use IndexedDB for structured progress and optional audio blobs; a small wrapper such as `idb` is sufficient. Use localStorage only for small preferences. Core use needs no sign-in, backend, paid API, LLM, API key or internet content fetch. No cloud sync, payment, admin portal or runtime AI tutor in this build.

Keep supplied content under `content/`; the site consumes it through a typed, validated repository. Do not copy lesson prose into UI components. Treat supplied IDs as stable. Preserve extra unknown content fields when importing later versions. Build-time validation should reject errors with the file and item ID. Split lesson loading by level rather than loading the whole course into the first page bundle.

Read `content/manifest.json` and `content-types.ts` first, then one representative lesson and scored exercise. Query relevant fields programmatically when needed; do not dump all JSON into the chat context. `scripts/validate-content.mjs` is a zero-dependency validator. `schemas/content.schema.json` defines core contracts; use the validator for references and musical invariants that schema alone cannot express.

## Product experience
Use a quiet music-practice interface: deep navy, warm off-white, teal accents, high contrast, generous spacing. Make the main action “Start today’s practice.” Desktop sidebar and a compact mobile navigation should give access to Today, Learn, Practice, Ear training, Resources and Progress. Group tools within Practice instead of filling navigation with every tool. Provide a clear light/dark preference, keyboard focus, reduced-motion support and large touch targets. Keep the fretboard scrollable on small screens without making the whole page overflow. Do not add a marketing landing page before the learning app.

1. **Today**: optional first-run preferences (name, goal, session minutes, handedness, timezone); continue current lesson, 30-minute plan, due reviews, timer and recent notes. Use device timezone by default. All counters derive from persisted records. The 28-day starter plan suggests a focus; repeat unfinished foundations rather than forcing advancement by date.
2. **Learn**: seven levels, 21 modules, 84 lessons. Display objectives, full teaching paragraphs, guided steps, common mistake/correction, application, exercises, question, sources and practical criteria. Keep every lesson browsable, label prerequisites as recommendations and level 5 as optional. Separate viewed, in progress, completed and self-assessed mastery. Navigation buttons must work for every lesson.
3. **Practice workspace**: tab with beat labels and a synchronised playhead; play/pause/stop, count-in, BPM with explicit beat unit, repeat count, bar-range loop, click volume, bass guide volume, drum loop selector and master volume. Include isolated metronome, generated reference tones and 12 original chord studies. Task exercises show their instructions and log controls without pretending to have playable tab.
4. **Fretboard/theory explorer**: EADG, frets 0–12 by default and 0–24 optionally; note names, sharps/flats, scale degrees, root/scale/chord selectors and sound on click. Show valid note positions for supplied formulas. Keep a stable labelled orientation; offer handedness mirroring without changing actual string numbers. Use key-aware note spelling: F# major includes E#, not F. Include the 69-term glossary and clear string/fret conventions. A bass-clef reference must explain that notation is written an octave above sounding pitch. Full score engraving is optional; readable rhythmic tab is required.
5. **Ear training**: all six modes and 120 supplied questions, with actual synthesised stimuli, replay, hidden answers until attempt, feedback, per-mode history and a review-mistakes option. Pitch-match practice is a separate self-assessment using generated target notes and the fretboard answer. “Octave up for listening” transposes all pitched stimulus events together and leaves answers/intervals unchanged. It must not change instrument tuning. Do not claim to hear a user's playing without an actual implemented input pipeline.
6. **Resources**: search titles/tags locally; filter by level, provider, topic and free/optional-paid access. Display publisher, purpose, checked date, access caveat and normal external link. Nine interactive pages require JavaScript. Online links are optional and should never block lessons. Do not scrape, copy, download or automatically iframe third-party content. No unverified video IDs are provided. If embedding is added later, use verified official URLs with click-to-load and a link fallback.
7. **Progress**: completed lessons, quiz results, ear results, actual practice minutes, milestone rubric, notes, best *self-reported clean* BPM and weekly activity. Never present time spent as playing accuracy. Due reviews follow the supplied intervals. Review success is an explicit learner action, not an automatic consequence of opening the lesson.
8. **Local practice journal**: text notes and optional microphone recording initiated by a clear button. Permission denial/unsupported recording must leave text notes usable. Keep recordings on device. Show size, playback, download and delete. Stop all media tracks when recording stops or the route unmounts; revoke blob URLs. Use supported MIME types via feature detection. Do not record automatically.
9. **Backup/settings**: export/import a versioned JSON backup of settings, progress, attempts, sessions and notes. Preview counts and validate before replacing data; confirm destructive replacement. Offer separate recording downloads, explicitly excluding audio blobs from JSON backups. Handle storage quota errors and explain that browser data can be cleared. Include “Reset progress” with confirmation. No fabricated synced state.

## Musical and playback correctness
All MIDI is **sounding pitch**: strings 4/3/2/1 are E1/A1/D2/G2, MIDI **28/33/38/43**. Frequency = `440 * 2 ** ((midi - 69) / 12)`. Tab top to bottom is G/D/A/E (string numbers 1/2/3/4). Frets are nonnegative and every note MIDI equals its open-string MIDI plus fret. The supplied twelfth-fret natural harmonic has the same pitch result; other harmonic nodes require their own rules.

Every scored exercise uses PPQ=96 and absolute `start_tick`. `barTicks = PPQ * 4 * numerator / denominator`. `seconds = ticks / tempo_unit_ticks * 60 / bpm`. Quarter BPM uses 96 ticks/beat, dotted-quarter uses 144, eighth uses 48. At 6/8 dotted-quarter=60, one bar is 2 seconds; at 7/8 eighth=140, one bar is 3 seconds. Do not silently interpret all BPM as quarters. Full event durations define layout; `gate_ratio` only controls audible sustain. Rests are silent, ghosts are short noise attacks. Long-short swing and triplets are already encoded in ticks; do not apply swing again. Articulation labels guide physical practice; synthetic tones do not demonstrate realistic slap, tapping or legato technique.

Use one audio transport for tab, click, guide tones and drums. Schedule ahead against `AudioContext.currentTime`; use animation frames for visual position only, not to trigger sound. Resume audio only after a user gesture. Ramp gains to prevent clicks, keep defaults quiet and clamp volume. Cancel scheduled sources on stop/unmount/restart; repeated Play must not create duplicate transports. All loops start at complete bar boundaries. Adapt only meter-compatible drum loops; disable incompatible choices with a readable reason. Route/tab visibility changes may suspend audio: stop cleanly, preserve state and require resume, without silently losing place.

A normalised ear stimulus uses `start_seconds` and `duration_seconds`, relative to the trial start. It is independent of practice tempo; the rhythm questions already contain their own count-in. Overlapping chord tones are intentional. Apply the same time origin to all voices.

Transposition must recompute chord names and bass pitches, respect slash notes and offer valid EADG positions. If a target falls below E1 or outside selected frets, offer an explicit octave change. Do not display negative frets or pretend this is a five-string instrument.

## Data and persistence
Use `schema_version` for content and a separate version for user data. Suggested stores: settings, lessonProgress, quizAttempts, earAttempts, practiceSessions, reviewQueue, milestoneAttempts, journalNotes, recordings. Give records stable IDs and UTC timestamps; retain local session date and timezone for daily activity. Migrate older user schemas explicitly. Timer minutes are active session time, not time spent on an abandoned background tab. Pause when hidden and avoid counting a paused timer. Update progress totals from records after every mutation, import and reload.

Learning completion: a lesson is complete when the learner confirms its practical criteria and answers its knowledge question correctly. A milestone uses at least 80% on the level's knowledge questions and practical confirmation in two distinct practice sessions. No automatic musical-skill score. Distinguish completion from an optional repeatable mastery assessment. Optional level 5 never blocks level 6.

Bundled data is available without live content APIs while the app is open. A full offline-reload/PWA cache is a stretch feature, not implied by using JSON. If implemented, verify it after a production build and show cached/offline status. External resources still need internet. No automatic resource rechecking at runtime.

## Delivery and verification
Build in this order: content repository + navigation + lesson completion; audio transport + tab + tools; ear training + studies; persistence + progress + backups; recording + responsive polish. Finish every core feature before reporting completion. Record short checkpoints in `IMPLEMENTATION_STATUS.md` so a later agent can resume without re-reading the conversation. Mark stretch work as omitted rather than leaving dead controls.

Run the supplied content validator, typecheck, lint and production build. Add focused tests for pitch/tick conversion, 6/8 and 7/8 tempo units, loop bounds, migration/import validation and progress aggregation. Browser-check desktop and mobile: first visit, every navigation destination, a scored exercise, a task exercise, three ear modes including chords/rhythm, lesson completion surviving reload, backup round-trip, rejected malformed backup, denied microphone permission, repeated Play/Stop, muted sound and visibility changes. Listen to one real playback session if the environment allows; otherwise report that limitation honestly. No screenshots or generated success claims stand in for working controls.

Provide exact run commands, what was implemented, checks run, and known limitations in a concise README. Keep external posting, hosting and cloud authentication out of this task unless the user separately requests them. A static deployment may be supported after validating the chosen build mode.
